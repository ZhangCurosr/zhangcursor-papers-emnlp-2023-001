# 论文速读：RepoCoder-Repository-Level-Code-Completion-Through-Iterative

## 一句话总结
本文提出 RepoCoder，一个通过迭代检索与生成（iterative retrieval-generation）实现仓库级代码补全的简单、通用且有效的框架，并构建了包含三种粒度（行级、API调用级、函数体级）的新评测基准 RepoEval。

## 研究问题与动机
1. **仓库级代码补全的挑战**：实际软件开发中，开发者编写代码时需要参考仓库中其他文件的上下文（共享工具、配置、跨文件API调用等），传统基于文件内的代码补全无法充分利用这些信息。
2. **现有方法的不足**：
   - 基于静态代码分析和启发式规则的方法（如统计语言模型）灵活性差，无法在任意位置生成任意长度的代码。
   - 在标注数据上微调的语言模型泛化能力有限，面对未见过的仓库需要重新训练。
   - 简单的检索增强生成（RAG）方法直接使用未完成代码作为查询，检索上下文与目标补全之间存在语义鸿沟。
3. **评测基准的缺失**：缺乏针对仓库级代码补全任务的标准化评测基准，现有数据集多为单文件内补全或特定API调用场景。

## 核心贡献（创新点）
1. **迭代检索-生成框架 RepoCoder**：首次将模型预测结果作为辅助查询进行迭代检索，有效缩小检索上下文与目标补全之间的差距；与简单 RAG 的本质区别在于利用多轮迭代让生成与检索相互增强，而非单次检索。
2. **新基准 RepoEval**：首个涵盖行级、API调用级、函数体级三种粒度仓库级代码补全任务的评测基准，并引入单元测试作为评估指标以提升准确性；与以往仅用相似度指标（EM/ES）的方法本质区别在于采用执行级别的正确性评估。
3. **广泛的实验验证**：在不同规模模型（GPT-3.5-Turbo、CODEGEN 6B/2B/350M）和稀疏/稠密检索器上验证了方法的有效性；与 prior 工作的区别在于系统性地证明了迭代检索在仓库级场景的普适性。

## 方法详解
**整体框架**：RepoCoder 将代码补全转化为检索增强生成（RAG）范式，并引入迭代机制。给定未完成代码 X，首先通过检索模型 $\mathcal{R}$ 从仓库代码片段集合 $C_{repo}$ 中检索相关片段 $C_{ret} = \mathcal{R}(C_{repo}, X)$，再由生成模型 $\mathcal{M}$ 输出补全结果 $\hat{Y} = \mathcal{M}(C_{ret}, X)$。对于第 $i$ 轮迭代（$i > 1$），使用上一轮预测 $\hat{Y}^{i-1}$ 构建新的检索查询，生成 $C_{ret}^i = \mathcal{R}(C_{repo}, X, \hat{Y}^{i-1})$，再输出 $\hat{Y}^i = \mathcal{M}(C_{ret}^i, X)$。检索器和生成器参数在整个过程中保持不变。

**代码检索**：
- 构建检索数据库：使用滑动窗口（窗口大小 $S_w$，滑动步长 $S_s$）遍历仓库文件，提取连续代码行作为片段。
- 第一轮的检索查询由未完成代码 X 的最后 $S_w$ 行构成。
- 第 $i$ 轮（$i > 1$）的检索查询由 X 的最后 $(S_w - S_s)$ 行与 $\hat{Y}^{i-1}$ 的前 $S_s$ 行拼接而成，以弥合检索与目标的语义差距。
- 检索模型可选稀疏模型（Jaccard 相似度）或稠密模型（UniXcoder 嵌入 + 余弦相似度）。

**代码生成**：
- 生成器为预训练代码语言模型，将检索到的代码片段按相似度排序后与未完成代码拼接成 prompt，格式如图3所示。
- 提示词中包含每个片段来源的文件路径，最大片段数 $K$ 受 prompt 长度限制。

## 实验与结果
**数据集**：RepoEval 包含 13 个来自 GitHub 的高质量开源仓库（2022年创建，Star ≥ 100），分为三组：
- Line Completion：8个仓库，1600个测试样本
- API Invocation Completion：8个仓库，1600个测试样本
- Function Body Completion：6个仓库，373个测试样本

**评估指标**：行级和API级使用 Exact Match (EM) 和 Edit Similarity (ES)；函数体级使用单元测试通过率 (Pass Rate, PR)。

**主要结果**（GPT-3.5-Turbo，行级补全）：
- Oracle: EM=57.75%, ES=75.43%
- In-File 基线: EM=40.56%, ES=65.06%
- RepoCoder Iter-2: EM=56.81%, ES=75.11%
- RepoCoder 相比 In-File 绝对提升超过 **10%** (EM) 和 **8%** (ES)。

**函数体补全**（GPT-3.5-Turbo，全部仓库平均）：
- In-File: PR=23.32%
- RepoCoder Iter-1: PR=38.34%
- RepoCoder Iter-2: PR=42.63%（达到Oracle水平）

**关键结论**：
- RepoCoder 在所有模型规模和任务设置下均显著优于 In-File 基线。
- 两轮迭代后性能趋于稳定，稠密检索器（UniXcoder）与稀疏检索器效果相当，验证了方法的鲁棒性。
- CODEGEN-MONO-350M 配合 RepoCoder 可达到甚至超越 In-File 的 GPT-3.5-Turbo 性能。

## 相关工作脉络
1. **静态分析与启发式方法**（Raychev et al., 2014; Svyatkovskiy et al., 2019, 2021）：依赖解析器识别上下文，无法生成任意长度的补全，灵活性受限。
2. **监督微调方法**（Hellendoorn & Devanbu, 2017; Svyatkovskiy et al., 2020; Ding et al., 2022）：在特定数据集上训练，泛化到新仓库成本高。
3. **大模型代码补全**（Chen et al., 2021; Nijkamp et al., 2022）：零样本生成，仅利用文件内上下文，忽略跨文件信息。
4. **仓库级提示构建**（Shrivastava et al., 2022）：使用启发式和分类器构建 prompt，方式不够灵活。
5. **检索增强生成**（Lewis et al., 2020; Lu et al., 2022; Zan et al., 2022）：单次检索辅助生成，未解决检索与目标间的语义鸿沟。
6. **生成增强检索**（Mao et al., 2020; Li et al., 2022）：在开放域问答和代码检索中探索预测辅助检索，但本文首次系统性地将其用于迭代仓库级代码补全。

## 局限性与未来方向
1. **低代码重复率仓库效果有限**：RepoCoder 依赖相似性检索，当仓库代码重复率低时，难以找到足够相关的上下文片段。
2. **最优迭代次数不确定**：多轮迭代可能导致性能波动（有的case上一轮对下一轮错），缺乏自动停止机制。
3. **实时部署的延迟问题**：迭代检索生成增加了推理开销，需通过量化、蒸馏、缓存等技术优化效率。
4. **未充分探索的方面**：prompt 模板设计、其他检索模型（如语义搜索）、先进生成模型（GPT-4、StarCoder）的适配、更多商业产品对比。

## 研究启发与可借鉴点
1. **迭代检索-生成范式**：将模型预测反馈给检索过程的思想可迁移到其他需要外部知识的生成任务（如文档问答、知识密集型NLP），值得探索"预测辅助检索"的通用框架。
2. **单元测试作为评估指标**：函数体补全引入执行级别评估（Pass Rate）而非仅用相似度指标，这一设计对代码生成评测具有参考价值，可推广至其他需要功能正确性的任务。
3. **滑动窗口构建检索库**：简单高效的代码片段提取策略，无需静态分析即可构建检索数据库，实现成本低且适用于新仓库。
4. **小模型+检索可匹敌大模型**：350M 参数的 CODEGEN 配合 RepoCoder 达到 GPT-3.5-Turbo In-File 的水平，为低成本部署提供了可行路径。
5. **查询构建的渐进式改进**：用部分预测替换原始查询的固定长度拼接策略（前 $S_s$ 行预测 + 后 $S_w - S_s$ 行原文）是一个简洁有效的设计，可借鉴于其他检索增强任务。

## 关键术语表
**RepoCoder**：本文提出的迭代检索-生成框架，用于仓库级代码补全。
**RepoEval**：本文构建的仓库级代码补全评测基准，包含行级、API调用级、函数体级三个子集。
**In-File Completion**：仅基于当前文件内上下文的代码补全方法，作为本文基线。
**RAG (Retrieval-Augmented Generation)**：检索增强生成，将外部检索信息与生成模型结合的方法。
**Exact Match (EM)**：预测结果与 ground truth 完全一致的二值指标。
**Edit Similarity (ES)**：基于 Levenshtein 距离的细粒度相似度指标。
**Pass Rate (PR)**：函数体补全中通过单元测试的比例，衡量功能正确性。
**Jaccard Index**：稀疏检索中计算查询与候选片段 token 集合交集与并集比例的相似度度量。

## 可复现要素
- **数据集**：RepoEval 基准公开于 https://github.com/microsoft/CodeT/tree/main/RepoCoder
- **代码**：已开源（同上链接）
- **权重**：使用 GPT-3.5-Turbo API 和 CODEGEN-MONO-6B/2B/350M 开源模型
- **关键超参**：
  - 最大 prompt 长度：GPT-3.5-Turbo 为 4096 tokens，CODEGEN 为 2048 tokens
  - 滑动窗口大小 $S_w$：行/API级为 20 行，函数体级为 50 行
  - 滑动步长 $S_s$：10 行
  - 最大检索片段数 $K$：10
  - 检索片段长度：prompt 长度的一半
